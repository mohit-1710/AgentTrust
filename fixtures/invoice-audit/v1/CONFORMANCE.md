# Controlled invoice-audit conformance suite v1

This suite checks the four committed public fixtures against the manually checked goldens described in [README.md](README.md). It supports only the claim `controlled_fixture_conformance_only` for `invoice.audit.v1`. The project-operated issuer and the two demo providers are controlled components. Passing these fixtures is not proof of financial correctness, arbitrary-input quality, liveness, independent reputation, or that a hostile provider runs the same implementation for paid requests.

`suite.json` names the fixture IDs in execution order and commits to exact CSV and golden JSON bytes using plain SHA-256, represented as padded base64. `conformance_suite_hash` is SHA-256 of `ASCII("AGENTTRUST_INVOICE_AUDIT_SUITE_V1\0") || exact suite.json bytes`, including its final LF. The `.gitattributes` file preserves CSV bytes and LF for the JSON commitments. Changing a fixture or golden requires updating the manifest and the owner-pinned suite hash; a suite revision is explicit.

`POST /v1/conformance` accepts exactly `{"fixture_id":"<named ID>"}`. Extra fields, paths, payment contexts and arbitrary CSV are rejected. The handler loads fixed public files, uses the same `auditCsv` engine intended for the paid route, and returns `{fixture_id, conformance_suite_hash, report}`. It does not need a credential, payment receipt or uploaded data. The identity and conformance functions are handler preparations; the actual HTTP server is T17.

`validateService(serviceId, options)` resolves only an operator-configured `(service_id, service_version)` catalog entry. The catalog must contain an exact canonical HTTPS origin whose endpoint hash matches the independently read registry record. No response-supplied URL or arbitrary origin argument is followed. This is a trusted two-provider configuration, not a general crawler or DNS/SSRF sandbox. All redirects are rejected; requests have a five-second timeout, and JSON responses are limited to 64 KiB. This preparation does not implement the optional localhost HTTP fixture mode.

Every run creates a random 32-byte nonce. The provider signs the native identity descriptor with its local merchant invoice key. The validator requires exact nonce, schema, network/core, service/version, payout, endpoint hash and registered invoice key, verifies the separate identity signature domain, and checks the 300-second maximum lifetime, five-second issue skew and strict expiry. The embedded descriptor key never supplies its own authority. The handler's default lifetime is 120 seconds. After all fixtures pass, the validator rereads the registry and checks the descriptor's expiry again.

A successful result contains an assertion **draft**, the evidence object and `evidence_json`. The evidence includes the signed descriptor and canonical descriptor hash, suite hash, exact raw response JSON and its SHA-256 for every public fixture. Preserve `evidence_json` exactly, without formatting or an added newline. `evidence_manifest_hash` is SHA-256 of `ASCII("AGENTTRUST_INVOICE_AUDIT_EVIDENCE_V1\0") || UTF8(evidence_json)`. Its separate domain and fresh nonce distinguish one run's evidence from the stable suite identity. The assertion pins `invoice.audit`/1, exact service version, suite version/hash, evidence hash and supplied expiry. Any failed identity, HTTP, registry or fixture check returns no assertion.

No credential is issued by this module. A separate owner/issuer helper must persist the evidence, recheck current identity immediately before sending, and submit the assertion through the issuer's authenticated `issue_credential` method. The contract also requires the exact current service version. Never pass issuer keys to the worker or MCP. The injected `readService` adapter must read the intended network/core at suitable finality; a provider's self-description is not a registry read. T14/T18 own that integration and actual issuance evidence.
