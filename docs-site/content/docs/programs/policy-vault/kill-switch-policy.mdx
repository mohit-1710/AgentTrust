---
title: "Pause and revocation"
description: "Stop new admissions without rewriting already-dispatched payments."
---

> Owner pause/revocation methods are implemented. The admission, retry and callback behavior below describes the frozen payment design; see [implementation status](/reference/changelog).

`set_policy(..., paused=true)` pauses the owner's new payment admissions. `revoke_session(session_id)` revokes a specific session. Both are direct owner management actions, not worker tools.

Contract revocation and removal of the protocol access key are separate operations. Removing the key stops it from signing new calls; revoking the session stops new admissions even if that key remains installed.

Already-dispatched operations keep their original accounting context. An authenticated exact retry can return the prior record without another payout, even after policy or session changes. If the protocol key has been removed, read-only payment views remain the way to inspect history.

Pause, profile edits and session revocation never release pending reservations or reset daily/dispatch counters. They also do not reverse a completed native transfer.

Repeating an already-completed session revocation is a no-op. A revoked session ID cannot be reused; register a fresh ID for a new assignment.
