> This page describes the frozen native design. Check [implementation status](/reference/changelog) before using an integration; a planned interface is not a deployed service.

A required profile pins this shape:

```ts
interface CapabilityRequirement {
  capability_namespace: "invoice.audit";
  capability_version: 1;
  conformance_suite_version: number;
  conformance_suite_hash: Hash32;
  accepted_issuers: AccountId[];
}
```

The namespace and version together identify `invoice.audit.v1`. Suite version is a nonzero u32. The issuer set contains 1–4 unique accounts. An empty required issuer set is invalid; `null` is the separate, explicit no-requirement choice.

For a new payment, the credential must match the selected issuer/ID/revision, service ID and identity version, capability namespace/version and pinned suite version/hash. Its dates must be valid and it must not be revoked. The run's `evidence_manifest_hash` is a separate commitment, not a substitute for the suite identity.

A worker cannot escape the requirement by putting a different profile in the invoice. Its session is bound to exactly one owner-assigned profile/revision. An owner trust entry also cannot override required validation.

The response is `require_validation` with a typed reason when this evidence is missing or unsuitable. That is a refusal to dispatch; it is not an automatic request to an issuer, payment authorization or owner approval prompt.

The issuer's assertion is limited to the named tested fixture behavior and service identity. It does not guarantee arbitrary output quality, honest future behavior or delivery.
