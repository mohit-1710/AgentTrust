---
title: "Ordered payment decisions"
description: "A deterministic sequence of checks before a new native payment can be dispatched."
---

> The evaluator and native dispatch are implemented. Check [implementation status](/reference/changelog) for the accepted testnet/runtime evidence and open refund-gap/model rehearsal gates.

The worker entry point must authenticate the actual caller and signing key, then check the owner-scoped payment ID. An exact existing invoice hash returns the original payment without dispatching again; a changed invoice under that ID conflicts.

New admission then follows these stages:

1. Active session, assigned/current profile, owner policy and network/core domain.
2. Canonical invoice, signature and current service identity/version/payout.
3. Explicit owner service and payout blocks.
4. Purchase/day/dispatch limits, spendable funds, storage credit, backing and capacity.
5. Required credential's accepted issuer, subject, scope, suite, revision, dates and revocation status.
6. Exact owner service trust for the assigned profile.
7. Reservation and native dispatch.

Trust never overrides a block or missing required capability. Registration is not owner permission. There is no one-off approval or score threshold that skips a stage.

The pure evaluator supports deterministic tests and the implemented client preview. Only the native write method can authenticate the real signing key and reserve funds. A preview explicitly reports `authorization: "not_proven_by_view"` and can become stale before execution.

An authoritative business rejection may emit a decision event without allocating a payment record. A transaction that panics must not be presented as a persisted rejection event. Rejected calls can still cost gas.
