---
title: "Dispatch rate limit"
description: "An owner-wide count of admitted dispatches in fixed 60-second buckets."
---

> This page describes the frozen native design. Check [implementation status](/reference/changelog) before using an integration; a planned interface is not a deployed service.

The first version counts dispatched attempts in fixed 60-second time buckets. The demonstration policy allows five dispatches in a bucket.

A newly admitted dispatch consumes one count. A later transfer failure does not restore it. A rejected request, preview or exact retry of an existing payment consumes no additional dispatch count.

The count belongs to the owner, not to an individual session or supplier. Creating another session and editing a policy cannot reset it.

Fixed buckets can allow a boundary burst around two adjacent windows. This is not a rolling-window limit or cumulative-spend velocity score. The daily monetary cap is a separate check.

`RATE_LIMIT` may include a `retry_after_ns` decimal-string timestamp. It is not permission to replace an unresolved payment's ID or invoice.
