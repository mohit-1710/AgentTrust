description: "Reservation, native transfer and callback outcomes are separate stages."

> This page describes the frozen native design. Check [implementation status](/reference/changelog) before using an integration; a planned interface is not a deployed service.

`execute_payment(quote, credential)` is the only worker money-moving method. It requires zero attached deposit, `predecessor_account_id == signer_account_id`, the invoice owner as signer and the actual signing key stored in the session. It must verify the canonical invoice against the registered merchant key and apply all policy gates before dispatch.

The payment ID is an owner-scoped nonce. Same ID plus same invoice hash returns the original operation; changed invoice content under that ID is `PAYMENT_ID_CONFLICT`. Credential references are admission evidence, not a way to change what an existing payment purchased.

| State | Meaning |
|---|---|
| `pending` | Admission reserved funds and scheduled the transfer; a terminal callback is not recorded. |
| `settled` | Transfer success was recorded by the private callback. |
| `failed` | A definitive transfer failure was recorded and the available claim restored once. |
| `needs_reconciliation` | Display label for a pending operation older than 120 seconds; funds remain reserved. |

Only a private callback from the core account with exactly one expected promise result may finalize a pending record. Duplicate callback processing must not finalize or refund twice.

A successful payout followed by callback failure leaves the payment pending. There is no automatic refund, resend or administrative resolver in this version. Historical views and receipts remain inspectable, but uncertainty does not authorize another payout.

The frozen limits are eight outstanding transfers (payments plus withdrawals) and 128 retained payment records per owner, with no automatic pruning. List views return at most 20 items. These are prototype bounds, not throughput claims.

`withdraw_available(withdrawal_id, amount_yocto)` is a separate owner-only operation. Its destination is fixed to that owner; pending principal, storage credit and operating funds are not withdrawable spendable balance. It follows the same backing and private-callback discipline and does not consume the worker's daily purchase budget.
