> This page describes the frozen native design. Check [implementation status](/reference/changelog) before using an integration; a planned interface is not a deployed service.

## The components

```text
Owner wallet / owner CLI -> core: funds, policy, sessions, trust and blocks
Merchant account       -> core: versioned service identity
Issuer account         -> core: scoped capability credential
Local worker -> SDK / MCP -> execute_payment -> native transfer
                                  |                  |
                              reservation      private callback
                                  +--- payment view --+
Worker -> service: signed quote / settled receipt / actual audit report
Website and docs -> read-only facts and clearly labeled evidence
```

These are responsibilities inside one shared native contract and its clients. There are no separate policy, settlement and credential deployments to configure.

## Authority and trust

The owner holds full-access management authority. The worker holds only a function-call key on the owner's account, restricted to `execute_payment` on the configured core and a finite gas allowance. A contract session also pins that actual signing key to one profile/revision and purchase limit. Session registration and protocol key installation are separate steps.

The merchant controls its service record; the issuer controls its credentials. An owner chooses which issuers and exact service identities to accept. Neither role can rewrite the owner's policy.

## Payment flow

A signed invoice binds network/core, owner/session, operation ID, policy/profile revisions, service/version/payout, endpoint and input commitments, asset, amount and dates. Admission reserves money and capacity before scheduling a transfer. Transfer and callback happen asynchronously; see [settlement invariants](/verification/atomic-tx-invariant).

The SDK must persist the exact signed attempt before broadcast. Timeout and an RPC result of not-found do not justify a fresh payment ID. A settled receipt can retrieve its original result after quote expiry; failure to retrieve it never triggers another payment.

## Prototype limits

The shared contract operator retains upgrade/full-access authority. The build does not claim immutable or production custody. A successful payout with a failed callback can leave funds recorded as pending indefinitely; there is no administrative refund/resend shortcut. Accepted issuers and the controlled providers are explicit trust assumptions, not proof of arbitrary service quality.
