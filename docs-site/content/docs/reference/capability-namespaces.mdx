---
title: Capability validation
description: How PolicyVault's optional capability check works against the ERC-8004 ValidationRegistry.
---

A policy can require that a payee hold a capability attestation before payments to it are allowed — for example a KYC tier, an audit attestation, or a compliance stamp. This is the optional sixth check in `PolicyVault.gate`.

Capabilities are attested in the canonical ERC-8004 `ValidationRegistry` at [`0x8004Cb1BF31DAf7788923b405b754f57acEB4272`](https://testnet.monadexplorer.com/address/0x8004Cb1BF31DAf7788923b405b754f57acEB4272). AgentTrust reads this registry; it does not deploy it.

## How the check works

When a policy enables a required capability:

1. `gate` looks for a matching attestation for the payee in the `ValidationRegistry`.
2. If no valid attestation exists, `gate` returns `RequireValidation` (not a `Deny`) along with the required capability.
3. The x402 server surfaces that as a `402` asking the user to obtain the attestation.
4. Once an attestor records the attestation on chain and the user retries, `gate` re-evaluates and the check passes.

A policy that does not enable a required capability skips this check entirely — most policies gate on caps, velocity, and reputation alone.

## Trust model

As with reputation, capability trust is payer-scoped: a policy decides which attestors it accepts for a given capability. There is no global allow-list — the integrator who owns the policy decides whose attestations count.
