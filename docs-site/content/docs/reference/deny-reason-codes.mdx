---
title: "Decision codes"
description: "Typed refusals explain why a new admission cannot proceed."
---

> These decision types are implemented in the local native domain layer. Check [implementation status](/reference/changelog) for runtime and client integration gates.

The serialized decision shapes are:

```ts
{ kind: "allow" }
{ kind: "deny", code: DenialCode, retry_after_ns?: U64String }
{ kind: "require_validation", code: CredentialFailure, requirement: CapabilityRequirement }
```

## Denial codes

| Group | Codes |
|---|---|
| Authority and owner state | `UNAUTHORIZED`, `SESSION_REVOKED`, `SESSION_EXPIRED`, `PAUSED`, `PROFILE_MISMATCH`, `POLICY_CHANGED` |
| Invoice and identity | `DOMAIN_MISMATCH`, `INVALID_INVOICE`, `INVOICE_EXPIRED`, `IDENTITY_CHANGED` |
| Owner blocks | `BLOCKED_SERVICE`, `BLOCKED_PAYOUT` |
| Limits and funds | `PURCHASE_CAP`, `DAILY_CAP`, `RATE_LIMIT`, `INSUFFICIENT_FUNDS`, `INSUFFICIENT_BACKING`, `STORAGE_CREDIT`, `CAPACITY` |
| Exact trust and attempt identity | `UNKNOWN_SERVICE`, `PAYMENT_ID_CONFLICT` |

## Required-validation codes

`MISSING`, `UNACCEPTED_ISSUER`, `WRONG_SUBJECT`, `WRONG_SCOPE`, `WRONG_SUITE`, `EXPIRED`, `REVOKED`, `REVISION_CHANGED`.

A credential refusal does not authorize the worker to change issuer policy or remove the requirement. A changed payment tuple requires resolving the original attempt, not overwriting it. An unresolved outcome is not a denial proving that no transfer happened.

Authoritative execution uses fixed gate ordering and one primary decision. Some parse/authority failures are transaction errors rather than persisted business-decision events. Preview, executed rejection and recorded replay must remain visibly distinct.

Owner configuration and registry methods also have fixed errors such as `UNFUNDED_ACCOUNT`, `REVISION_OVERFLOW`, `INVALID_PROFILE` and `INVALID_DATES`; those are not an extra worker decision or approval feature.
