---
title: "Canonical wire format"
description: "Borsh field order, fixed widths and exact byte commitments."
---

An invoice is the ASCII domain `AGENTTRUST_NEAR_INVOICE_V1` plus a zero byte, followed by Borsh fields in this order:

```text
schema_version:u8, network:string, core_account:AccountId, owner_id:AccountId,
session_id:[u8;32], payment_id:[u8;32], policy_revision:u32,
profile_id:string, profile_revision:u32, service_id:AccountId,
service_version:u32, payout_account:AccountId, endpoint_hash:[u8;32],
request_hash:[u8;32], asset:string, amount_yocto:u128,
issued_at_ns:u64, expires_at_ns:u64
```

Integers are little-endian. Strings carry a u32 UTF-8 **byte** length. Binary hashes/keys/signatures are fixed arrays without a vector-length prefix. Network and asset are strings, not enum discriminants. Ed25519 signs these bytes directly; `invoice_hash` is their SHA-256.

String lengths vary, so do not assume one global offset table applies to every invoice. The shared vectors annotate exact offsets for each input. Their Unicode/large-integer case includes values above JavaScript's safe-number boundary.

JSON U64/U128 fields are canonical unsigned decimal strings. Binary JSON fields are canonical padded base64 of exactly 32 or 64 decoded bytes. Account IDs use native validation. Profile IDs are 1–64 UTF-8 bytes without normalization. Unknown fields and malformed encodings reject.

Small u8/u32 numeric fields use finite integral parsed-number semantics: `1`, `1.0` and `1e0` have the same canonical integer; `-0` encodes zero. This does not create a floating-point path for money or timestamps.

The descriptor uses its [separate domain and schema](/reference/discriminator-constants). A signature cannot substitute across the two message types.
