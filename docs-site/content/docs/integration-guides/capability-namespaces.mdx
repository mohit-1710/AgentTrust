---
title: Capability validation (integration)
description: Enable a required capability on a PolicyVault policy and let the gate route unattested payees through RequireValidation.
---

A policy can require that a payee hold a capability attestation — a KYC tier, an audit attestation, a compliance stamp — before payments to it are allowed. Capabilities are attested in the canonical ERC-8004 `ValidationRegistry`; PolicyVault reads it.

This is the optional sixth check in `PolicyVault.gate`. Most policies gate on caps, velocity, and reputation alone and never enable it.

## Enable a required capability

When a policy declares a required capability, `gate` checks the ERC-8004 `ValidationRegistry` for a matching attestation for the payee. With no valid attestation, the gate returns `RequireValidation` instead of `Allow` — the x402 server then asks the user to obtain the attestation.

## How the gate consumes it

```
1. gate runs caps → velocity → reputation as usual
2. if the policy requires a capability:
     - look up the payee's attestation in the ValidationRegistry
     - none / expired / revoked → RequireValidation
     - valid attestation present → Allow
```

After the payee obtains an attestation and the user retries, the gate re-evaluates and the check passes.

## Trust model

Capability trust is payer-scoped: the policy decides which attestors it accepts for a capability. There is no global allow-list — the integrator who owns the policy decides whose attestations count. This is the same local-trust model the reputation check uses.
