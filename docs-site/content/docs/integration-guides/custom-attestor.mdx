title: "Issuer validation flow"
description: "Validate a pinned endpoint and a public fixture suite before issuing a scoped credential."

> This page describes the frozen native design. Check [implementation status](/reference/changelog) before using an integration; a planned interface is not a deployed service.

The demonstration issuer is operated by the project and explicitly accepted by the owner. Its assertion is a bounded trust claim, not a decentralized reputation score or runtime attestation.

The planned validation procedure is:

1. Read the current service identity and resolve its configured HTTPS origin.
2. Check the origin's endpoint commitment against the registry.
3. Send a fresh random nonce to `POST /v1/identity-challenge`.
4. Verify the signed descriptor against the registered key, nonce, network/core, service/version, payout, endpoint and dates.
5. Call `POST /v1/conformance` with only committed public fixture IDs; compare responses with manually checked goldens.
6. Record separate suite and run-evidence hashes, including the verified descriptor hash.
7. Re-read the registry version before issuing the credential through the issuer account.

The conformance route cannot accept arbitrary user CSV. This avoids making the validator pay for an unqualified service before it can test it, without exposing the paid arbitrary-input audit for free.

A passing fixture run does not prove that an untrusted provider uses the same code for every future purchase. The contract cannot observe HTTP liveness or output quality. Current identity, accepted issuer, scope, expiry and revocation must still be checked for each new payment.

Keep issuer keys out of the buyer's SDK/MCP process. Issuing a credential never grants the issuer permission to change the owner's policy or spend the owner's funds.
