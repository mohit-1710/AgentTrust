title: Custom attestor
description: How capability attestations are recorded against the ERC-8004 ValidationRegistry so PolicyVault's capability check can pass.
---

An attestor vouches that a payee holds some capability — a KYC tier, an audit attestation, a compliance stamp. Attestations are recorded in the canonical ERC-8004 `ValidationRegistry` at [`0x8004Cb1BF31DAf7788923b405b754f57acEB4272`](https://testnet.monadexplorer.com/address/0x8004Cb1BF31DAf7788923b405b754f57acEB4272). PolicyVault reads that registry when a policy enables the capability check.

AgentTrust does not deploy the `ValidationRegistry`; it is a canonical ERC-8004 contract on Monad. This guide describes how an attestation flows into a gate decision.

## Lifecycle

```
1. payee (subject) requests validation for a capability
2. attestor verifies the off-chain claim (KYC doc, audit report, etc.)
3. attestor records the attestation in the ERC-8004 ValidationRegistry
4. PolicyVault.gate now finds the attestation → capability check passes
5. attestor can later revoke → gate returns RequireValidation again
```

## How the gate consumes an attestation

A policy that enables the capability check accepts attestations from a payer-chosen set of attestors. When `gate` runs:

- No valid attestation for the payee → `RequireValidation`.
- A valid, unexpired, unrevoked attestation from an accepted attestor → the check passes and the gate can `Allow`.
- An expired or revoked attestation → treated as absent: `RequireValidation`.

## Trust model

Only attestations from the attestors a policy accepts count. There is no global registry of "approved attestors" — the integrator who owns the policy decides whose attestations they honor, the same local-trust model the reputation check uses.
