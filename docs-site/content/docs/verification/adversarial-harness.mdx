title: "Adversarial cases"
description: "Authority, identity, limits and retry failures to verify before claiming a complete flow."
---

The acceptance matrix requires at least these failure classes:

- Arbitrary first caller, relayed context, wrong worker account/key and attempted owner-management bypass.
- Revoked/expired sessions, stale policy/profile revisions and attempts to choose a weaker profile.
- Forged or changed invoice fields, wrong network/core and changed service payout/key/endpoint/version.
- Explicit service/payout blocks, unknown service, purchase/day/dispatch limits and insufficient funds/storage/backing.
- Missing, wrong-issuer, wrong-subject/scope/suite/revision, expired or revoked credentials.
- Concurrent reservations, midnight/policy edits, definitive transfer failure and callback duplication.
- Successful transfer with failed callback, unresolved outcome, same-ID changed content and restart after lost broadcast response.
- Pending/wrong receipt attempts to obtain content, or settled receipt reuse with changed CSV.

Pure tests cover deterministic logic where possible. Actual protocol key restrictions and host receipt/refund behavior require the separate native runtime lane. The HTTP/MCP route also needs its own schema/retry and final-receipt checks.

A simulated or preview refusal is not an executed on-chain rejection. Store provenance for each observation; link a real rejection receipt only when one exists.

This inventory is a required test contract, not a claim that every case is already passing. See [current status](/reference/changelog).
