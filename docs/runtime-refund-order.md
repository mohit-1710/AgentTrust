# Native refund/callback order: bounded source audit

Original source audit: 11 November 2026, read-only, against nearcore tag 2.14.0 sources already downloaded under `.sprint/nearcore-2.14/`. NEP-616 corroboration was checked 12 November UTC / 13 November IST. No runtime, database, chain, test, funding or deployment operation was executed for this source note. It is not a T13 pass or a reproduced scheduling result.

## Conclusion

**Callback-before-liquid-refund is not ruled out by this source.** [NEP-616's description of existing refunds](https://github.com/near/NEPs/blob/master/neps/nep-0616.md#L230-L244) explicitly says the runtime does not guarantee that a refund arrives before callback execution. The pinned runtime has a conditional path: a failed transfer creates its balance-refund receipt before its callback Data receipt, but the outgoing router can buffer the refund while forwarding the Data receipt. The Data receipt can then activate an already-postponed callback before the refund arrives. The relevant difference is positive Action-receipt congestion gas versus zero Data-receipt congestion gas; generation order alone provides no FIFO guarantee for newly generated receipts.

This establishes a source-supported possible scheduling path under the stated routing conditions. It does not establish that the current default Sandbox configuration reaches those conditions, or that a specific public-network execution did so. Keep `refund_gap` explicitly unavailable/unrun until an actual controlled capture exists. Retain the real-balance admission guard.

## Verified source facts

1. On a failed action receipt, `deposit_refund = total_deposit`; refund generation runs before outgoing Data generation. The balance refund is appended to `result.new_receipts`, then output Data is appended later. [runtime.rs1047–1072](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/lib.rs#L1047), [1295–1304](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/lib.rs#L1295), [1402–1417](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/lib.rs#L1402), [1152–1191](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/lib.rs#L1152).
2. Without an explicit refund override, the balance refund receiver is the failed receipt's predecessor. The core's native transfer therefore returns its principal to the core. A balance refund is an ordinary Action receipt containing a Transfer from system. It is not an instant receipt: that classification only covers PromiseYield and eligible single DeleteAccount actions. [receipt.rs428–430](https://github.com/near/nearcore/blob/2.14.0/core/primitives/src/receipt.rs#L428), [473–512](https://github.com/near/nearcore/blob/2.14.0/core/primitives/src/receipt.rs#L473).
3. Each newly generated non-instant receipt independently calls `forward_or_buffer_receipt`. This function tries forwarding the current receipt, then buffers only that receipt if it cannot fit. It does not refuse a newer receipt because an earlier one for that shard was buffered. The earlier `forward_from_buffer_to_shard` loop does stop at its first non-fitting buffered receipt, but this does not impose a barrier on later newly generated receipts. [runtime.rs1193–1235](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/lib.rs#L1193), [congestion_control.rs292–325](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/congestion_control.rs#L292), [338–385](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/congestion_control.rs#L338).
4. Forwarding requires both sufficient remaining gas allowance and byte allowance. Refusing a receipt leaves those allowances unchanged; forwarding subtracts its gas and size. [congestion_control.rs402–462](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/congestion_control.rs#L402).
5. Action receipt congestion gas includes execution/send fees and attached function gas, without a system-refund exemption in this calculation. Data receipt congestion gas is explicitly zero. Receipt size is Borsh serialized length. [congestion_control.rs678–735](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/congestion_control.rs#L678), [964–967](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/congestion_control.rs#L964).
6. When the final awaited Data receipt arrives, the receiver loads and immediately executes the postponed Action receipt. It does not wait for an unrelated balance-refund receipt. Incoming receipt processing follows the incoming vector, subject to compute/proof limits and delay queues; it cannot restore the original source-vector order once routing separated the receipts. [runtime.rs1440–1514](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/lib.rs#L1440), [2693–2736](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/lib.rs#L2693).
7. Same-shard routing uses unlimited gas allowance (`Gas::MAX`), although byte grants still exist. A default small single-shard Sandbox run may therefore never exercise the cross-shard gas-budget path. [congestion_control.rs96–120](https://github.com/near/nearcore/blob/2.14.0/runtime/runtime/src/congestion_control.rs#L96).

## Conditional inference and limits

The independent routes for refund and callback data permit the callback to execute while the refund is delayed. A callback that restores aggregate available claims can therefore precede the corresponding incoming liquid balance. This is a source-level possibility, not an observed AgentTrust outcome.

The source read did not prove the complete bandwidth/congestion scheduler's attainable state space for the current Sandbox genesis, nor reproduce the required shard mapping/timing. Do not report this as an exploit, a measured frequency, or a universally observed order. Conversely, the absence of a gap in an uncongested ordinary run is not proof that the conditional path cannot happen.

## Evidence still missing

The accepted native capture does not show a callback completing while the principal refund is still uncredited, nor a later contract-level `INSUFFICIENT_BACKING` refusal during that state. The prior shard-congestion proposal was automatically rejected and remains unrun. Leave V17/G2 open; source analysis and final snapshots do not substitute for independently obtained native evidence.

No production fault API, account-balance patch, runtime-policy bypass, or new recovery authority is recommended. The existing default-off callback-failure artifact establishes a different V18 scenario and cannot substitute for V17 refund-gap evidence.

## Fixture feasibility checked on 12 November

The pinned ordinary Sandbox RPC exposes state patching and fast-forward, without a supported receipt pause/release selector. Adversarial block/chunk controls require separate `test_features`; the `sandbox` feature does not enable them. [Feature definitions](https://github.com/near/nearcore/blob/2.14.0/nearcore/Cargo.toml#L98). No node or database was started for this follow-up.

Full congestion can reject a transaction before AgentTrust executes, which is not evidence of its backing guard. [Congestion admission](https://github.com/near/nearcore/blob/2.14.0/core/primitives/src/congestion_info.rs#L79). A genesis runtime-config override also does not generally tune the current protocol: the inspected store applies that override to protocol version zero. [Configuration construction](https://github.com/near/nearcore/blob/2.14.0/core/parameters/src/config_store.rs#L79).

The separate midnight case was later captured and accepted as V15 evidence in [the native report](native-runtime-evidence.md); it does not establish V17. Fast-forward changes virtual time and can produce normal blocks around epoch transitions; it does not freeze in-flight receipts. [Fast-forward](https://github.com/near/nearcore/blob/2.14.0/chain/client/src/client_actor.rs#L1141), [virtual time](https://github.com/near/nearcore/blob/2.14.0/chain/client/src/client.rs#L1766). The refund-gap case remains open; map-host tests and final failed-transfer observations are supplementary evidence.
